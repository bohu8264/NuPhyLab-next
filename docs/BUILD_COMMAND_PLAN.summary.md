# 同一条命令，生成两端安装包

## 打算怎样使用

**参考 NuPhyHub 最新设计，两端统一使用 Bash 的 release 命令。** release 在这里表示优化编译并打包，不代表功能已经全部验收。下面是拟定用法，尚未实现：

```bash
bash ./nuphylab release
```

Mac 在终端运行，Windows 使用 Git Bash（Windows 上的 Bash 环境），分别生成本系统的安装包。不能在一台 Mac 同时打两端包，也不支持用 WSL 构建 Windows 包。安装包使用者无需安装 Bash 或 Node。

## 默认先生成候选包

Mac 生成稳定证书签名的应用和 DMG，默认不提交 Apple 公证。Windows 生成完整程序目录和 EXE 安装器，默认未签名，会清楚标明。

需要公证时，Mac 在命令后加 `--notarize`；需要代码签名时，Windows 加 `--sign`。代码签名用于核对软件发布者，不要求先开启自动更新。工具或证书不齐就报错，失败不会自动降级。

## 签名失败可以接着做

借鉴 Hub，Windows 签名失败后保留构建记录与已完成部分。之后用 `sign` 加本次构建目录恢复，只做剩余签名与封包，不重新编译。源码、文件或证书变了就拒绝恢复，避免混入别的包。Mac 公证恢复暂不纳入这个入口。

## 怎样确认拿到的是哪一包

每次构建有独立目录，记录版本、源码来源、签名和公证结果、文件校验值。过程显示当前步骤、耗时和日志位置；失败现场不会混进分发目录。

打包不会自动安装、启动、上传，也不清空作品或结束负责恢复键盘的进程。产品身份和数据目录保持原样，不承诺测试版能独立并装。Mac 现有更新设置沿用，Windows 更新仍关闭。

## 接下来怎么落地

先实现入口、环境检查和构建记录，再接签名恢复，最后在两端生成真实包验证。用 `doctor` 检查环境，用 `release --dry-run` 先看计划。新 `build` 仅作同义入口；已有 npm 命令保持原义。

本次只更新方案，批准后再开发。真实签名、公证及灯光、改键、AI 等功能验收分别记录，不能用打包成功代替。
