### 本轮：原生 Codex 已有任务窗口（2026-11-11）

**新增源码入口，尚未进入现有安装包或实机验收。** Codex 页面可明确点击“切到正在运行的任务窗口”，不要求终端由本次 Lab 创建。仅尝试能核对的传统独立控制台，不发送按键、问题或审批，也不启动第二个会话。

- 网页只提交固定操作名、来源和完整 UUID，不能指定 PID、创建时间、程序路径、窗口或输入。新宿主声明能力后才可用，Claude 页面不提供这个入口。Tauri/Node 操作清单同步到版本 14，后台准备动作使用独立字段白名单。
- 原生探针新增只读 `writerTargets`，一次只接受一个完整 UUID。根据任务锁文件向 Restart Manager 查询资源使用者，保留所有程序名称和完整创建时间符合的 Codex 候选。没有候选、多个候选、查询失败或旧探针不认识新操作时均拒绝，不任取第一条；原有状态查询仍可使用。
- 回复保留 PID、完整程序路径及 FILETIME 创建时间。64 位时间以 16 位十六进制文本传输，Node 用 BigInt 核对其与毫秒时间一致，避免数字精度损失。后台前后两次查询必须得到同一 PID、完整创建时间和程序位置，程序须与当前发现的本机 CLI 一致、文件仍存在、任务仍在列表中。

### 此前：自有终端窗口核对与切回（2026-11-11）

**新增的是源码入口，当前安装包尚不包含恢复或切回功能。** 用户在 Windows AI 页面明确点击“切回 Lab 打开的终端”时，宿主按来源及完整 UUID 查找本次应用实例创建进程时保存的系统句柄。没有持有、进程已退出或身份未知时拒绝；不会按标题、项目名、最近活动或 PID 猜测其他窗口，也不重新启动会话。

- 网页仍只提交来源、会话编号和固定操作名，不接受 PID、窗口句柄、路径、参数或按键。代理清单升为版本 13，只有新宿主声明切回能力时按钮才可用。恢复和切回共用忙碌保护，重复点击不会并行操作；切换工具来源后丢弃旧反馈。

### 功能键的只读检查（上一轮基础）

Windows 档的标准 F 键无需照搬 Mac 的改键流程。先完整观察当前映射，才能分清标准键、系统功能和使用者的自定义设置；这一阶段不做接管、吞键或 AI 快捷键操作。

原生 `keymap::capture` 在 8 秒总预算内，通过 B2 读取当前物理档位的基础层，通过 B1 读取 Mac/Win 两个出厂基础层。每层包含矩阵及额外按键，共 `(rows × columns + extraKeys) × 2` 字节；56 字节分包，保留最后短包，以大端 16 位数解析。只读取基础层，不推断 Fn 组合层的用途。三层完整读取两遍，再核对固件、密钥、档位及完整矩阵信息；任何变化、校验或路由错误都丢弃整份结果。只允许有界、偶数字节的 B1/B2 读取，传输层在发送前拒绝 B3 改键、B4 重置及不合范围的请求。

### 内置灯效的独立事务

`output/native.rs` 只处理 Kick75、精确恢复固件 4.0.18.6，原状态须为模式 1–20。关闭状态或逐键自定义状态在新基线及任何写入前拒绝，提示先用官方工具选一种内置灯效。原生 USB 身份门槛未扩大：当前只登记了 Air75 V3 的身份族，真实 Windows Kick75 仍需身份核对，不能用模拟的 qualified 状态作为放行依据。旧版 4.0.15.6 没有因此取得恢复资格。

接管只读取和刷盘保存原设置、动态颜色采样，不发 D6，也不进入自定义模式 21。应用仅修改主灯模式、亮度、速度和可选颜色；未请求字段、侧灯及图案预设保持原值。不发 D8 调色板写入，不发 F3/F5 休眠命令。参数不变时不发 D6。独立 D5 读回、前后身份核对及采样前后的设置一致才确认成功；动态颜色采样不作为可恢复调色板的证据。

内置模式和逐键模式使用同一个受监督进程内的不同租约。Node 不能在内置租约发送逐键或侧灯命令，也不能绕过持有者另开探针。模式间切换先恢复并归档原记录，再建立新的租约。设置被外部改变或确认失败会停止该租约并尝试一次原设置恢复，不自动重发不确定写入。异常结束留下的内置原记录由已有冷恢复页处理；因原状态是内置模式且从未改写调色板，冷恢复只需设置写入和读回，不需要调色板记录。

灯光私有契约在 v3 增加 `armNative`、`nativeLighting`、`nativeSnapshot`，本轮已升级为上节说明的 v4；当前预览命令清单为版本 11，默认只读 v1 的新增读取能力见上节。旧灯光进程与新客户端混用会拒绝握手，构建资源必须配套更新。应用只接受模式 1–20、亮度 0–100、速度 0–4 及可选六位颜色；页面不能提交路径、设备身份或租约。Windows 的 Kick75 入口显示“内置灯效”标签，逐键绘图仍可切回；旧 Mac 兼容页面保持原行为。

本轮自动检查覆盖设置不变时零写入、调色板/侧灯/休眠不变、非法参数与不支持原状态、外部改动、错误确认、独立读回不一致、旧协议拒绝、队列过期、优先退出、进程异常结束后的显式冷恢复，以及应用在内置和逐键模式间切换。检查使用临时目录和模拟设备，不连接真实 HID，不代表 Windows Kick75 或 Air75 V3 新固件实机通过。

上一轮内置灯效验证：共享 Node 回归 1089 项，1088 通过、1 项 Windows 专用进程检查在 Mac 跳过；Node/Rust 原生进程契约 15 项全部通过。Rust 工作区 155 项通过，另 3 个隔离子进程入口由父测试单独运行、默认列表显示忽略。UI TypeScript/Vite 构建、工作区 Clippy 及 Windows x64 原生目标全入口 Clippy 通过；构建仍有既有前端大包提示。宿主路由的三项测试确认内置参数、额外字段和敏感操作边界。独立 Chrome 使用模拟 Tauri 通道实际检查应用的应用/恢复按钮、1440/960 宽度，以及两份概要各自桌面/窄屏、深浅主题、目录开合跳转和相对链接；无页面异常或横向溢出。以上不等于 Windows WebView2、完整 Windows 安装器或真实键盘验收。

### 桌面采集与隐私

`nuphylab-desktop-io` 只负责输入观察与声音采集，没有 HID writer、恢复目录或通用 shell。使用独立 JSONL 管道、随机会话、单调事件序号、请求上限、心跳和停止回执。Node 不接受页面伪造声音数据或原生按键事件。Raw Input 不设置 `NOLEGACY`，不更改普通按键和数字 0 的系统行为。

监听前原生层枚举全部支持的 USB 控制接口，必须只有一个且型号匹配；直接内嵌编号已经核对后，再要求 Raw Input 输入接口归属相同的唯一 USB 父节点。只匹配 VID/PID 不够。原始编号、接口路径和该关联不通过页面或 Node 传入。任何键盘设备变化立即失效，普通状态中仅报告能力。Fn 没有通用 Windows 扫描码，不登记为可监听键。

系统输出采用 WASAPI loopback，麦克风采用共享采集。PCM 支持有界整数/浮点格式、声道合并和 FFT，仅发送音量与八个频段。设备更换、失败及系统休眠/唤醒会清空旧采样并停止当前效果；再次播放需要明确操作。独立进程意外结束后最多重建三次，不自动开始采集或监听。它可以单独被停止，负责键盘恢复的进程仍不被强杀。

### Windows AI 状态与钩子

SQLite 3.54.1 官方 x64 工具的 URL、归档 SHA-256/SHA3-256 和程序 SHA-256 固定在 `windows-runtime-lock.json`。下载有超时和大小限制，不加载扩展，查询使用 `-readonly -safe -init NUL`。Node 使用随包工具，不依赖系统 sqlite3。许可随包提供，详见第三方声明。

进程探针只读取进程基名、PID 和启动时间。Codex 线程写者由 Restart Manager 对固定锁文件查询，重新比对进程启动时间，不读取进程参数、不用 mtime 推断运行中、不结束进程。拒绝查询、结构不匹配或证据不足均保留未知状态。

Claude 钩子将固定 Node 运行时复制到应用数据的自有位置，以 `command + args` 直接执行脚本，避免 Bash/cmd/PowerShell 二次解析。保留其他设置、其他钩子和默认保留的事件记录；自有项可从页面移除。使用可移植编码文件名，避免 Windows 保留名和冒号问题，升级时合并旧、新事件文件并去重。只保存最小状态事实，不保存 prompt、tool_input、令牌或问题正文。运行时与脚本摘要经过缓存校验，文件变化时重新计算，不每次轮询读取整份运行时。

恢复命令只复制、不执行。项目路径按 PowerShell 单引号字面量转义；打开文件夹必须是仍存在的本机绝对目录。页面只提交当前任务 ID，后台重新解析任务，不接受自定义程序、命令、路径、目标窗口或按键证明。Raw Input 事件不具备敏感动作凭证；Windows 实体 AI 控制仍未完成。

```bash

```

该入口按用户要求参考 Talkflow 的交互式沃通/UKey 流程，默认使用 `C:\SignTools\wosigncodecmd.exe`、证书指纹 `68B94B194F597BA6E2694113268FE3956A041FEF` 和 `http://timestamp.digicert.com`，同目录须有 `wosigncode.exe`。无需设置环境变量；`NUPHYLAB_SIGN_TOOL`、`NUPHYLAB_CERT_THUMBPRINT` 和 `NUPHYLAB_TIMESTAMP_URL` 仅用于可选覆盖，无效覆盖报错，证书不可用时不自动改选。每次运行在签名时安全输入一次 PIN，旧 `NUPHYLAB_SIGN_PIN` 不能跳过输入，空输入失败且不重试；构建进程不继承 PIN 或更新私钥。主程序和五个配套程序、最终 setup 逐项验签并核对时间戳；固定 NSIS 标记后禁止封包改写已签字节，成功目录含安装器、校验值和构建清单。自动更新保持关闭，不生成更新签名/元数据，不上传、不安装、不主动启动 GUI。当前只实现 Windows `release --sign`，补签和其他统一命令未实现。实际证书签名及安装升级尚未验收，详细命令及自动检查记录见 [独立签名说明](BUILD_COMMAND_PLAN.summary.html)。

原完整更新发布入口继续使用 `npm.cmd run windows:release`，可追加 `-- --offline-installer`。构建前必须提供有效的 `windows-release.json` 公共配置、Windows 证书存储中的证书、`NUPHYLAB_CERT_THUMBPRINT`、HTTPS 的 `NUPHYLAB_TIMESTAMP_URL`、允许域名内的 `NUPHYLAB_DOWNLOAD_BASE`，以及秘密环境中的 `TAURI_SIGNING_PRIVATE_KEY`。私钥及口令不写入仓库、文档或日志。脚本对五个随包程序签名，Tauri 对主程序及 NSIS 安装包签名，再核对全部产物的可信证书与时间戳；缺任何条件都不生成新的发布清单。发布目录要求只含本次安装器，避免选中旧构建。

发布输出含平台更新元数据和产物大小/SHA-256 清单，但不自动上传或发布。自动更新采用 Windows 系统 TLS 证书链、最低 TLS 1.2、HTTPS 及准确域名限制，下载最多 512 MB，验证 Tauri minisign 签名、Windows 发布者与时间戳，并将暂存文件重新绑定到已验签的字节。页面只能请求检查或安装刚检查到的版本，不能指定下载 URL、安装器路径或参数。安装前必须取得本次后台的绑定退出回执、确认键盘恢复及进程正常退出；失败不启动安装器。当前配置关闭，页面只提示使用完整本地安装包。

手动安装、升级及卸载也不能强杀恢复进程。`installer-hooks.nsh` 在锁定的 Tauri CLI 2.12.4 中覆盖默认的 `CheckIfAppIsRunning` 宏，改用只读的进程检查，最多等待约 20 秒；仍有应用或配套进程、查询失败或超时便停止。它不调用 RmShutdown、taskkill 或 Stop-Process。安装/卸载阶段建立会话内命名对象，应用在启动 Node 之前独立检查；对象存在或无法核对时不启动后台。完成后释放对象，失败或进程结束由系统释放句柄。编译用的固定 PowerShell 编码和对象名称由版本化契约与可审核脚本生成，限制 NSIS 字符串长度，不手工维护另一份脚本正文。实现对照锁定版本的 [Tauri 安装模板](https://github.com/tauri-apps/tauri/blob/tauri-cli-v2.12.4/crates/tauri-bundler/src/bundle/windows/nsis/installer.nsi)、[进程检查宏](https://github.com/tauri-apps/tauri/blob/tauri-cli-v2.12.4/crates/tauri-bundler/src/bundle/windows/nsis/utils.nsh) 与 [NSIS System 插件](https://nsis.sourceforge.io/Docs/System/System.html)。安装器生成与真实升级仍需 Windows 验证；本机没有 Windows 资源编译器，不能据此声称 NSIS 已编译通过。

失效的采集进程与 HID 恢复进程分别处理：前者没有设备设置、恢复记录或派生子进程，可在确认实际进程和管道都结束后退场，不能伪造正常停止回执；后者始终要求原有严格的恢复证据。关闭期间不再重建采集进程，防止遗留新后台。

## 先检查 USB 接口

正常退出已安装的 NuPhy Lab、NuPhyIO 及其他键盘控制软件，再用 USB 数据线连接一把键盘，切到有线模式。先仅枚举：

```powershell
npm.cmd run windows:probe
```

结果列出型号、VID/PID、usage、接口及传输类型。此命令不打开设备。`controlCandidate` 为 true 表示满足 USB 和 usage 初步筛选；不等于该接口已经通过报文验证。没有候选时保留结果，不更换驱动、不尝试普通打字接口，也不手改型号表。

再明确执行读取：

```powershell
npm.cmd run windows:probe -- --connect
```

探针要求只有一个候选接口，打开后检查无编号的 64 字节输入/输出报告，再发送 A1、A0、D1 读取身份、布局、物理 Mac/Win 档位和灯位。每个响应检查长度、标记、checksum 和路由，读完即关闭句柄；不发送 D6/D8、B3、F5 或 EE，不修改灯光、键位和休眠设置。`readOnly: true` 和 `WINDOWS_PROBE_ONLY` 是本阶段状态，不应通过固件升级来消除。普通探针连接不读取 D5/D2 或 F3，灯效和休眠检查需在设备页分别触发。

- 故意结束宿主后，后台应通过控制管道关闭或心跳超时执行清理。此项只在本阶段只读探针上测试，后续写入功能需单独验证恢复。
- 灯光、声音、AI 命令和更新操作应明确不可用，不能假装已经成功。

本次远程启动使用 `target/debug/nuphylab-desktop.exe`，在已登录的 Windows 桌面会话中运行；需要保留同一源码目录下已准备好的 Windows resources/binaries，不能仅分发这一个调试可执行文件。已确认窗口标题为“NuPhy Lab · Windows 预览版”、窗口响应正常、后台只监听回环地址且宿主建立了连接。SSH 会话可能无法枚举其他桌面会话的窗口，需在对应桌面会话核实，不能仅凭 SSH 中句柄为 0 判断启动失败。

Tauri 前端只调用受限的宿主命令，宿主代理访问自己启动的本机服务，认证 token 不提供给页面。原生事件不能通过普通前端命令伪造。M0 仅开放作品、本地设置和只读连接相关操作。

## 只读桥接握手与错误处理

`shared/contracts/native-readonly-v1.json` 是只读原生协议的内容源。Node 的 `server/native-contract.mjs` 读取它，Rust 的 `native/core/src/bridge.rs` 在编译时纳入。Windows 与模拟 Tauri 启动描述默认启用该协议；Mac 原有启动描述保持无握手的兼容路径。

| 检查 | 当前规则 |
| --- | --- |
| 连接前确认 | 先发送 `hello`，核对协议版本、实现名称、平台、实现版本、会话标识和只读能力；不匹配时不发送设备命令 |
| 消息边界 | 单行最多 32 KiB，含换行符，按 UTF-8 字节计算；允许跨读取分片拼接，超限、通道结束时消息未完成、错误编码或无效 JSON 被拒绝 |
| 排队与等待 | 最多 32 个待完成请求，包含正在执行的一项；一次只发送一项，握手最多等待 3 秒，普通请求最多等待 12 秒 |
| 请求身份 | 正整数编号严格递增，限制在 JavaScript 安全整数范围内；普通命令不能覆盖编号、操作或夹带其他参数 |
| 会话与事件 | 每次进程启动生成新的会话标识；事件包含同一标识和递增序号。旧回复不能命中当前请求，旧事件或乱序事件使该连接失效 |
| 能力与退出 | 拒绝灯光写入、键位、输入和声音操作；只读状态不得宣称已接管。正常请求退出需收到该会话的 `shutdownComplete` 与 `noMutation: true`，不能只看退出码 |

协议错误或等待超时会撤销该连接的确认状态，取消旧队列并关闭输入管道，让桥接自行清理；后续新进程重新握手，不回退到 Mac 协议。`device.nativeBridge` 单独报告桥接检查结果，与 USB 键盘是否连接分开表示。只读协议没有写入或恢复日志，`noMutation` 表示未修改设置，不代表当前实体固件的设置恢复已通过验收。

`windows:probe -- --connect` 也通过同一个客户端完成握手；枚举模式仍不打开设备。旧后台资源与新桥接混用会报版本/能力不匹配，需正常关闭预览后运行 `windows:prepare` 重新准备配套文件，不应通过升级键盘固件处理。

`windows:test` 先构建本机 Rust 桥接，再执行专项测试。`tests/windows-native-bridge.test.mjs` 使用管道替身注入版本不符、超长输出、错误事件、进程中断和队列拥堵；`tests/contracts/windows-native-process.test.mjs` 使用真实 Rust 程序检查握手、未握手读取被拒绝、写入被拒绝和错误输入清理，不发送会被接受的连接或枚举命令，因此不打开真实 HID 设备。

## 键盘档位与只读灯效检查

更新资源并重新启动后，设备页显示 A0 返回的物理 Mac/Win 档位，不从电脑系统推断。正常只读连接使用中性的预览状态；后台失联、多把键盘或真实错误仍按原规则显示，旧设备信息不能当作本次连接的结果。Windows 在独立恢复区域显示检查与恢复结果，不接受页面提供的恢复成功证据。

`shared/keyboard-models.mjs` 保存完整恢复固件、`lightingStateLength` 和写入规则。独立的 `shared/contracts/lighting-read-schemas.json` 额外登记 Air75 V3 2.0.0.7 的 22 字节只读结构；Rust、Node 及资源共用该登记。旧版 1.0.23.6 的恢复规则保持不变；其他型号按原配置读取 17 字节。读取资格不能授予播放、恢复或休眠写入资格，未登记版本继续拒绝 D5/D2，不建议为测试升降固件。

设备页的“读取灯效信息”对应预览命令 `inspectLighting` 和原生操作 `lightingSnapshot`：

1. 打开唯一 USB 控制接口，重新读取 A1/A0/D1，检查固件、几何、灯位与物理档位。
2. 固件完全匹配才发送 D5，使用该档位作为 handle，校验设置长度与字段范围。AIR 的 shape-speed 原始读取可能超出设置接口范围，保留原字节，不当作可直接写回的参数。
3. D2 按 RGB 字节地址读取，每块最多 54 字节，地址及长度均为 3 的倍数；同时验证回复路由、校验和及加密/明文路由形式。
4. 再次读取身份、固件和档位，发生变化即丢弃整次结果。一次原生读取的总截止时间为 8 秒，单次交换最多 1.2 秒；每次操作结束即释放 HID 句柄。
5. Node 再核对型号、固件、档位和只读标记，仅在内存保存与连接会话及进程代次一致的结果。断开、重连或身份变化后清除，不自动沿用旧采样。

结果包含原始设置和当前颜色采样，固定报告 `readOnly: true`、`noMutation: true`、`restorationReady: false`。动态灯效可能在分块读取期间变化，采样不是原调色板或同一时刻的完整画面。它不写恢复日志、不写入键盘，也不提供恢复能力；设备页仅显示采样数量和亮度，不把未经灯位映射核对的颜色画到按键上。2.0.0.7 的写入资格来自前述独立登记，不能由该只读结果提供。

## 恢复日志核心

`native/core/src/recovery.rs` 是 M2 的恢复存储基础，不依赖 Tauri、Node、HID 或界面。`output` 报文核心和显式灯光入口调用它，Windows 默认只读命令仍不调用；默认只读协议中的 `lightingWrite` 和 `recoveryJournal` 仍为 false，点击只读检查不会创建恢复记录。恢复库回归使用临时目录和模拟 USB；本轮有限实机核对见最前面的当前证据。

| 项目 | 当前规则 |
| --- | --- |
| 记录绑定 | 型号、VID/PID、完整已核对固件、Mac/Win 档位和设备身份全部匹配；有可靠序列号时绑定序列号，否则绑定本次连接，不自动跨连接恢复 |
| 目录与锁 | 调用方提供已经建立的可信私有设备目录；目录固定文件名，不从作品或前端路径选取；系统文件锁避免协作进程同时使用，进程退出后释放 |
| 原始记录 | `profile-0.json` / `profile-1.json` 保存原设置和颜色采样，独占创建并刷盘、回读，不覆盖已有记录；任一档位有旧记录、残留调色板、写入意图或完成标记时，阻止新基线；整键盘休眠记录未处理时也阻止新基线 |
| 原调色板 | 单独保存在对应 `.palette.json`，绑定原记录的完整文件摘要；仅接受带设备绑定、全亮度原采样及重建结果的证明，加载时重新计算；重复保存相同内容可复用，禁止替换原值 |
| 格式与损坏 | 版本 1 的独立 Windows JSON 封装，严格字段解析，最多 16 KiB，SHA-256 校验内容；校验用于发现损坏，不代表设备身份认证；不自动读取或迁移 Mac 旧日志 |
| 进入设备操作前 | 设置操作要求原记录完整并持久化 `.intent.json`；D8 前另需原调色板证明和绑定其摘要的 `.rgb-intent.json`。前后核对绑定和磁盘原文，变化或不确定失败后使输出租约失效，不盲目重发；报文核心另重新读取固件、密钥、档位和句柄代次 |
| 重启与恢复 | 重开旧记录后只开放恢复路径；失败保留原文。旧记录缺少写入意图时返回 `RECOVERY_CONFIRMATION_REQUIRED`，不自动推断未发生写入；无可靠序列号时冷重连不能自动恢复 |
| 验证完成 | 仅接受报文核心生成、绑定本事务和最后写入序号的内部恢复凭据；普通回调、离线比较、页面布尔值均不能代替。归档全部活动原文，刷盘、回读后保存 `.completed.json`，才清理匹配的活动文件 |
| 清理中断 | 目录锁内校验完成标记、历史摘要、记录归属及所有剩余活动文件，之后仅继续文件清理，不操作键盘；不同活动文件、损坏历史或未列出的残留均保留并停止，历史副本始终保留 |

文件系统实现使用独占创建和 `sync_all`。Unix 文件权限为 0600，并同步目录；Windows 使用显式共享模式及打开重解析点的标志，拒绝选定目录和日志文件中的重解析点。当前检查以调用方建立的可信目录为边界，已与下述固定设备目录及 ACL 守卫组合；长路径、杀毒占用、突然断电和可移动磁盘仍需验收。Rust 核心声明最低工具链 1.96，便于固定文件锁及其他标准库 API 的基线。

保存日志本身不等于完整可恢复备份。调色板采集、D6/D8 报文、分阶段读回及成功后的清理已在下述模拟事务中串联；原生写入命令与后台生命周期已接入，当前固件有限实机核对见首节；完整使用与故障验收仍待集中进行。只读 `LightingSnapshot.restorationReady` 仍为 false；它不签发恢复资格，M2 完整故障验收仍待完成。

## 调色板与恢复计算规则

`native/core/src/lighting_policy.rs` 根据公共型号配置生成的 `lightingRecoveryPolicy` 选择规则。AIR75 V3 1.0.23.6、Kick75 4.0.18.6 使用各自的精确规则，其余六种已核对的 17 字节 S4 配置使用明确登记的保留字段规则；未知规则或 AIR/Kick 固件与规则不配套时拒绝加载。Windows 的 Air75 2.0.0.7 另由精确登记选择独立规则，不改这些默认配置。Mac 的 Swift 生产实现未被替换。

- **调色板证明**：只有已核对固件、完整灯位采样、自定义模式 21、100% 主灯亮度和 RGB 模式 1 才能重建；旧版 AIR 还要求主灯颜色为白色，新版 2.0.0.7 允许非白主色，但最大通道须为 255。AIR 的 200/255 量化及最后一个键灯的两路额外缩放分别对照对应版本证据。每个输出字节寻找精确前像，没有对应输入就拒绝。重建结果表示同样的全亮度输出，不能据此声称找回了唯一的原始存储字节。
- **保留计算依据**：`ReconstructedPalette` 保存版本、绑定、观察到的设置、完整 RGB 和确定的重建值。日志不再接受任意 RGB 数组作为调色板；保存、重开时检查证明，即使外层校验和被重新计算，不符合条件的采样也不能通过。旧的无证明文件被拒绝并保留，不静默猜测或覆盖。
- **主灯颜色编码**：AIR 的主灯 RGB 会经历 HSV 和整数舍入。直接把读回颜色写回可能偏色；旧版恢复使用 Float32 模型，新版使用独立整数模型，再以有界搜索找到读回值完全相同的输入，找不到时保留原记录并停止。
- **拥有字段与历史**：设置计划只生成地址 0 的 17 字节数据，不生成 HID 写报文。AIR 保留实时镜像字段 5 及预设字段 17–21，忽略未实现的 13；Kick 的 17 字节保持严格比较；其余已核对配置仅忽略未实现的 5/13。需要保留预设变化时，日志规划器先将活动记录原文独占写入摘要命名的历史文件并刷盘、回读，相同历史复用，冲突停止。最终读回期间出现的预设变化也先存档。
- **分开验证**：先用全亮度自定义采样比较原调色板，取得与本次原记录绑定的独立读回结果，再比较最终拥有字段。系统预设或动画模式正确也不能绕过调色板比较；自定义原灯效还必须与原键灯采样一致。量化导致调暗后不一致时，可以计算仅调整不匹配通道的上界候选，但仍必须以真实读回验证，不能降低比较标准。
- **原全黑状态**：固件不能通过设置接口保存模式 0；必要时规划为静态模式 2、主灯及侧灯亮度为零。原状态未变时可避免设置写入。验证要求全部灯位为黑色，只说明可见灯光全黑，不声称移动了物理总开关。

`Transaction.plan_restoration` 和 `assess_restoration` 将这些规则与磁盘原记录绑定；其他原始记录的计划、错误档位或错误调色板读回会被拒绝。离线比较本身不会删除活动日志；只有下述报文核心签发的恢复凭据能进入完成流程。调暗后颜色候选的纯计算仍保留，但当前事务原型拒绝调暗或带过滤的自定义原状态，不把候选算法当作已完成的支持。

对照样本保存在 `tests/fixtures/windows-lighting-recovery.json`。生成器抽取现有 Swift 的完整型号枚举及选定计算函数，在独立临时目录编译运行，不链接 HID。需要更新时在 Mac 执行：

```sh
node scripts/windows/generate-recovery-fixtures.mjs
```

样本包含 4,096 组 RGB/读回/精确输入、141 组逐字段状态、八种型号的调色板上下界及物理输出映射，另有 402 份完整 D6/D8 报文（八型号 × 两档位 × 三种密钥，包含每个颜色分块）和 9 份 F3/F5 休眠报文。Swift 生产函数独立生成帧头、加密、校验和及物理地址，Rust 逐字节对照。Windows 只需已提交的 JSON，不需要 Swift。Node 检查公共配置、提取源码与生成器摘要；文本摘要统一处理 LF/CRLF。CI 已加入该样本路径；这些测试不是 Windows 11、实体输出、驱动或安装验收。

## 原始报文灯光事务

`native/core/src/output.rs` 通过 `Transport` 抽象处理原始 64 字节请求和回复，不依赖窗口。Windows 的现有只读适配器已实现该传输接口，并继续由只读入口使用；默认入口不接受 `arm`、`paint` 或真实恢复 RPC；新增的独立灯光入口需显式选择，现行只读能力清单保持不变。

1. **采集与范围检查**：同一控制句柄上读取身份、固件、Mac/Win 档位和灯位，再按“设置→完整颜色→设置”采集基线，拒绝期间发生的设置变化。只有默认配置或独立登记的精确固件可进入灯效操作。自定义原状态须为模式 21、主亮度 100、RGB 模式 1；旧版 AIR 要求白色主色，新版允许最大通道为 255 的主色。调暗/过滤的自定义原状态在任何写入前拒绝，无法精确编码回原设置的状态也拒绝。
2. **备份与接管**：基线刷盘后再次核对实时设置；原本已是自定义模式时，先核对原键灯颜色并保存证明。用一条 D6 切换到全亮度自定义状态，等待并独立读取 D5；原本是系统灯效时，再读取原隐藏调色板并保存证明。任何 D8 前都必须具备该证明。
3. **限定输出**：D6 仅允许地址 0、17 字节拥有字段；D8 依公共型号的 `rgbWriteIndices` 将矩阵顺序转换为物理地址，每包最多 13 条键灯记录，不写侧灯地址。映射必须是完整且无重复的键灯排列。侧灯通过 D6 字段设置。RGB 编码器不生成 B3 键位或 F5；休眠 F5 仅由下述专用模块生成一字节启用标记，不提供时间参数写入。
4. **确认与停止**：每次写入前后确认句柄代次、固件、密钥和档位；确认回包必须路由、校验和、内容均一致。超时或错误不会重发设置/颜色。设置仅有限次重读 D5；第一帧/明确要求的完整帧独立读取 D2，其余帧可只发送变化键灯，相同帧仍检查租约和原记录。接管期间主模式被外部修改时停止绘图。
5. **恢复与证明**：恢复前先存档需要保留的预设变化；如保存了调色板，先切回全亮度自定义状态、写回全部原键灯、按型号等待并独立读回。再恢复最终拥有字段并检查原自定义可见颜色或全黑状态；系统预设模式正确不能替代调色板验证。仅此路径能产生不可序列化、不可由页面构造的完成凭据。
6. **作用域退出**：`Session` 在首次接管写入前取得事务所有权；正常作用域退出、操作错误和 Rust 异常展开均会尝试恢复。灯光和休眠独立处理，一项失败或展开不跳过另一项，已验证部分可独立归档退休，失败项保留。显式 `close` 返回完成或失败；监督器和析构不会再次盲试。强制终止/机器崩溃仍需下一次经过绑定验证的恢复会话。刚建立、确定未发起写入的记录只归档清理，不用旧设置覆盖后来手动修改。

单次核心操作预算为 30 秒，每次交换最多 1.2 秒；整个普通操作共享预算，恢复阶段各自取得新预算。只读入口仍为 8 秒，原 Node 只读请求为 12 秒；新应用驱动单独使用 120 秒灯光客户端，宿主采用 135 秒退出契约。设备身份、工厂、客户端、私有目录及正常退出已经组合；冷启动检查/明确恢复页面已接通，实体故障验证仍待集中进行。

`Connection.serial` 只允许调用方提供已经核对为稳定且唯一的序列号；Windows 仅在原生身份层验证直接内嵌字符串、USB 父节点及唯一标记后提供序列号；其余情况保持空并绑定句柄，不把任意非空字符串视为可靠身份。Air75 V3 2.0.0.7 现在按前述独立 Windows 规则进入此事务，仍要求稳定身份及可验证原状态。八种型号的模拟报文覆盖不代表八种型号正式支持。

## 灯光控制器与进程监督（早期 v1 设计）

`native/core/src/controller.rs` 将报文事务接入独立的输入、设备与回复执行路径。新增 `shared/contracts/native-lighting-v1.json`，与原 `native-readonly-v1.json` 完全分开。`Backend` 标明模拟或 Windows HID，由可信调用方选择；事务测试使用模拟后端。Windows 主程序默认选择只读契约，新增 `--lighting` 单独选择新控制器，但不增加页面路由。早期独立 Node 灯光客户端当时仅用于开发测试；当前应用选用独立 v4 契约，稳定身份门槛及固件规则仍不能通过能力值绕过。

| 边界 | 控制器规则 |
| --- | --- |
| 启动与会话 | 3 秒内完成新协议握手；未握手或未收到 `arm` 不调用设备工厂。每条命令检查会话及严格递增的安全整数编号，拒绝额外字段、错误类型、旧编号与其他会话 |
| 路径与设备 | 现有可信恢复目录和打开唯一控制接口的工厂由原生调用方提供，不接受页面或请求指定路径；设备和文件操作始终由一个执行线程拥有 |
| 租约 | `arm` 返回本进程递增的灯光租约；`paint`、`side`、`restore` 必须匹配。恢复完成后新接管分配新租约，旧报文无效；历史未恢复时禁止建立新基线 |
| 背压 | 输入队列和回复队列各最多 8 条；满队列停止普通输出并进入恢复。排队超过 500 毫秒的逐键、侧灯颜色返回 `FRAME_EXPIRED`，不重放，租约仍可处理新帧 |
| 存活与取消 | 独立输入线程处理有效请求与心跳；建议每秒心跳，5 秒无有效联系即撤销普通输出。EOF 和 `quit` 不等待旧颜色队列排空，直接取消；晚到心跳不能复活失效租约 |
| 设备检查点 | 传输包装器在交换前后及分段等待时检查存活。停止后不发送后续普通报文；已经开始的一次交换仍受原有 1.2 秒上限约束，不承诺撤回已发出的 USB 数据 |
| 设备预算 | 采集、休眠接管与 RGB 接管共用本次普通操作的 30 秒设备预算；有效心跳不能无限续期。后续有效绘图/侧灯命令重新计时，传输按剩余预算及单次 1.2 秒上限取较小值 |
| 恢复 | `begin_recovery` 不因父进程失联拒绝恢复读写；RGB、休眠两个恢复阶段分别重新获得 30 秒设备预算。监督器使用 `finish_once` 取得已完成的自动回滚或做一次关闭，失败不在退出时再次重放 |
| 回复与退出 | 设备线程只向有界回复队列提交消息，阻塞 stdout 不占用设备线程。最终清理事件之后不再接收回复；排空等待最多 3 秒，失败可返回异常但不倒退已完成的设备恢复 |
| 强制终止 | 杀死原生进程时无法继续执行恢复；系统释放锁，活动原文和写入意图保留，下次接管被阻止。后续设备确认与恢复入口仍待接入 |

接管失败时，`start_with_rollback_report` 报告已验证的内部回滚结果；没有完成凭据时按未确认处理。最终事件绑定握手会话和顺序，报告 `lightingRestored`、`recoveryPending`、`noMutation` 与原因。该事件只说明本进程的事务；没有打开设备时，`noMutation` 只表示本进程未写入，不能据此清除其他设备或旧连接记录。故障之后即使恢复成功，进程仍可返回失败退出码；独立 Node 灯光客户端同时验证回复、清理事件和进程退出，不能把任一布尔值或退出码单独当成完整成功。

新契约和独立 Node 灯光客户端采用 120 秒请求等待，覆盖普通设备预算、两个独立恢复阶段及回复排空，不表示正常帧需要等待这么久。该等待值只用于新客户端，应用选用的原只读客户端仍为 12 秒。预算在传输检查点撤销后续报文，不能承诺中断操作系统内阻塞的打开接口或磁盘刷盘；这些仍需实机故障验收。心跳必须独立发送，不能排在灯光请求的串行队列尾部。宿主关闭等待、主动取消和 UI 停止动作也需单独组合验证，不能直接复用当前只读关闭流程。控制器 `restore` 按已接受命令顺序处理；需要立即终止旧输出时走优先退出/输入关闭路径。

隔离子进程测试实际创建操作系统管道和临时目录，执行 EOF、缺失心跳及强制终止；不打开 HID。单元用例用私有可控时钟和同步信号精确触发超时、积压与在途取消；生产入口始终使用单调时钟和契约默认值，不提供外部时钟或超时覆盖。完整结果见下方验证记录。

## 独立 Node 客户端与 Windows 持有句柄传输

- **选择绑定**：`arm` 请求必须指定已识别的 `modelId` 与 `lightingProfile`，禁止附加路径、序列号或超时配置。Rust 在创建原灯效记录、读取休眠及写包前检查所选型号和档位。接管回复包含型号、完整固件、VID/PID、灯位数及连接 token；客户端逐项核对，拒绝不匹配的回复。
- **严格通信**：`native-lighting-contract.mjs` 校验所有回复及清理事件；两种协议共用 `native-jsonl.mjs` 的有界 UTF-8 行读取器，只读契约保持不变。后端必须明确为 `simulated` 或 `windows-hid`，不允许模拟程序冒充真实设备。
- **背压与心跳**：最多七个普通请求，串行发送，预留独立心跳容量；每秒心跳，确认等待最多三秒，覆盖 Rust 五秒失联期限。客户端等待中的颜色超过 500 毫秒即丢弃，Rust 再检查自身队列。恢复取消尚未发送的旧颜色；立即停止用优先 `quit`，不等绘图请求排空。
- **结束证据**：正常关闭同时需要本次 `quit` 回复、会话绑定且顺序有效的最终清理事件、正常进程退出。故障后即使恢复成功也保留失败及恢复证据。协议错误按恢复未确认处理；只结束输入以请求原生清理，不自动杀死、重启或重放。晚到回复不能复活旧租约。
- **Windows 传输**：`native/windows/src/transport.rs` 拥有句柄。原只读连接继续保留八秒总预算；库中的 `open_lighting_transport` 没有该短寿命限制，改由控制器逐操作和逐恢复预算限定。单次交换最多 1.2 秒，支持原有两种输入报告形式；短写、校验错及超时均不重发。唯一 USB 接口与描述符筛选仍保留，序列号仍为 `None`。
- **测试组合**：`native/core/examples/lighting-simulator.rs` 仅供开发，使用与核心单元测试共享的模拟板，不依赖 HID，不随安装包提供。`npm run windows:test` 构建此示例并运行真实 Node/Rust 灯光互通测试；所有文件写入中文、空格临时目录。原只读 Rust 互通测试继续执行。

该客户端已由 `WindowsHardware` 接入应用基本播放及停止/退出路径，使用独立 Native 进程。冷启动恢复页面和实体故障验收仍待补充，开发模拟器不用于真实设备。最新换线复查后已重新准备资源及界面并启动预览，安装包仍保留原构建。

## 整键盘休眠租约（旧版独立规则）

`native/core/src/output/sleep.rs` 负责 F3/F5、独立读回和设备核对，`recovery/sleep.rs` 负责原记录及完成清理。规则限定 Air75 V3、19F5/1028、完整固件 1.0.23.6 和可靠序列号。Windows 本轮仅在直接内嵌编号、USB 父节点与唯一标记均匹配的已核对 AIR 家族上提供 `serial`；其他情况仍为 `None`。2.0.0.7 只读 F3 可用；本轮 F5 未取得确认，最终写入登记关闭，详见首节。其他型号不发送休眠报文，未扩大硬件支持。

- **字段范围**：F3 固定全局地址 0、handle 0、长度 4；F5 固定同一全局路由、长度 1，仅写 0/1 启用标记。后三字节仅保存和比较，不猜测单位，不写休眠时间或保留值。九份 Swift 报文样本覆盖三种密钥的读取、禁用和恢复。
- **独立原文**：`board-sleep.json` 不含灯光档位，绑定型号、VID/PID、完整固件和可靠序列号；`board-sleep.intent.json` 在任何 F5 前刷盘，绑定原文摘要。与 RGB 共用设备目录锁及严格有界 Windows 文件封装，不自动读取或迁移 Mac 的旧休眠文件。
- **接管**：`Session` 在 RGB 基线存好且取得作用域所有权后，先处理休眠，再接管 RGB。原本已关闭自动休眠时不建记录、不发 F5；已有旧记录时先阻止新基线，不能把当前 0 值当成原状态。每次普通 RGB 写包前后检查休眠原文及意图，丢失或变化即停帧。
- **写入核对**：发送前再次读取全部四字节，外部变化即拒绝；确认回包后再独立 F3 读回。设置已生效但确认丢失时不重发禁用，作用域尝试恢复原标记。确认回包但实际未变化也不能通过。已接管标记被外部重新启用时停止灯光，不反复禁用。
- **分别恢复**：关闭时先尝试 RGB，再尝试休眠；其中一项失败或 Rust 展开不跳过另一项。只改启用标记，保留实时的后三字节；物理 Mac/Win 档位变化允许同设备的全局休眠恢复，但固件、密钥或句柄变化仍拒绝写入。每项的独立读回通过后，才归档并清理该项，整体关闭需要两项均完成。
- **退出和重开**：休眠原文与意图逐字节归档、完成标记刷盘后，才删除匹配活动文件。清理中断后重开仅继续文件处理，不发送 F5；不同活动文件、损坏标记或历史均保留。监督器不重试失败恢复；原生进程被强制结束时只能保留文件。
- **单独恢复 API**：`recover_board_sleep` 留给可信原生调用方处理已有休眠记录，不依赖 RGB 档位。重新打开的句柄须具备匹配的可靠序列号及固件，旧记录无写入意图时拒绝自动推断。该底层函数不直接暴露给页面；当前通过独立维护协议的 `recoverExisting` 组合调用，冷启动检查和确认流程已接入。

新控制协议的 `boardSleepLease` 是模块能力；接管回复另报告本设备 `supported`、`active`、`pending`。应用基本播放使用此独立租约和正常退出恢复，没有新增休眠设置按钮或时间写入。2.0.0.7 不获取此休眠租约。启用标记写入、断电持久性、挂起和长期运行仍未验收。

## 异常重开后的显式恢复（已接入应用）

`native/core/src/output/recover.rs` 提供 `recover_existing`，仅由可信原生调用方提供设备、型号、已经建立并持有锁的私有目录，以及实际物理档位。它不建立新原文，不获取播放租约，不自动开播或切换 Mac/Win 档；现已通过独立灯光 v2 协议和 Windows 恢复页面显式调用；默认只读协议及 CLI 参数没有新增路径、编号或强制恢复覆盖。

- **身份前提**：目录与完整型号配置一致，使用稳定唯一序列号、完整固件及所选物理档位重新核对，旧 token 不足以授权。AIR 本轮核对了原生序列号来源与换口稳定性，其他设备继续拒绝无证据的身份；2.0.0.7 另有已登记的灯光规则；读取本身仍不授予恢复权限。
- **残留查询**：`JournalStore::recovery_status` 在已持有目录锁的范围内检查两个档位的原文、调色板、设置/颜色意图及完成标记，以及三种全局休眠活动文件。孤立或损坏文件仍算待处理；目录、链接或不可检查的路径返回错误。只查看存在状态，不解析成成功凭据，不修改或清理文件。应用查询使用新的 `open_existing`，要求锁文件已存在且不进行完成清理。原 `open` 初始化行为保持兼容；显式恢复才分别校验并续清理当前灯光和全局休眠的完成记录；某一项失败不会跳过另一项。
- **分别恢复**：当前档位的 RGB 和全局休眠各尝试一次，包括一项损坏、通信失败或 Rust 异常展开的情况。继续沿用 RGB/休眠各 30 秒的独立设备预算、单次 1.2 秒交换及独立读回；失败保留相应原文，成功项归档退休，不盲目重复已经完成的项目。
- **完成含义**：报告分别给出 `notNeeded`（没有对应记录）、`restored`（有验证完成结果）、`failed`（失败及原因），并给出延后的档位和实际残留。只恢复当前物理档位；另一档位仍待用户明确处理。即使其他档位文件在过程中被外部删掉，也不能把它算作已恢复。报告只用于状态展示，不能构造或代替底层的封闭恢复凭据。
- **完成标记保护**：事务检查增加 `.completed.json` 阻止条件。目录打开后若出现完成标记，旧事务在发包前即停止，需要先核对原文及历史的文件清理，不能重新操作键盘。
- **独立进程验证**：测试进程先接管、绘图并把模拟硬件状态保存到临时文件；父测试真正终止该进程，再启动新进程重新取得系统锁及恢复旧记录。覆盖一次全部成功、RGB 失败但休眠成功、休眠失败但 RGB 成功；部分成功后第三个进程仅恢复失败项。模拟文件代替独立于应用存活的实体硬件状态，不是 USB 硬件证据。

八种型号的重新打开恢复在模拟传输中验证；休眠仍只处理已核对旧版 Air75 V3。可信目录、原生身份、查询/恢复操作、应用页面和宿主等待已组合；本轮有限实机结果见首节，完整人工验收仍未开始。完整 v2 流程见下文。

## Windows 私有恢复目录（由独立灯光进程持有）

`native/windows/src/storage.rs` 导出的 `RecoveryRoot`、`DeviceDirectory` 由可信原生设备工厂调用，已通过独立灯光进程接入应用。默认只读进程和页面不能直接传入或选择恢复路径。实际灯光接管现在在身份及固件通过后使用该私有目录；记录查询仅打开已有目录，不存在时返回无记录。实机核对产生的历史原记录保留，不作为临时编译文件清理。

| 边界 | 实现与限制 |
| --- | --- |
| 固定位置 | 通过当前用户 `SHGetKnownFolderPath(FOLDERID_LocalAppData)` 定位 `NuPhyLab/native-recovery-v1`；正确初始化/配对 COM 和内存释放。不采用 `LOCALAPPDATA` 环境覆盖，不提供公开自定义路径入口 |
| 创建权限 | 从进程 token 取得用户 SID；`CreateDirectoryW` 创建时附带该用户所有者及受保护 DACL，只有当前用户与 SYSTEM 两条可继承完全控制规则，没有先宽后改的窗口 |
| 已有目录 | 根、型号及设备槽均以实际句柄检查所有者与严格 ACL；宽权限、空 DACL、未保护或额外规则均拒绝，原权限和数据不变。已有 `NuPhyLab` 上层目录不被自动改权限 |
| 路径稳定 | 从本地磁盘根逐层保留目录句柄，不共享 DELETE；检查重解析属性，拒绝符号链接、junction 等重定向及 UNC。目录守卫随日志持有到锁释放以后，支持本地中文及超过 260 字符的路径 |
| 型号命名空间 | `model-<摘要>` 绑定版本、型号和 VID；不含 PID、固件、档位或连接 token，避免这些变化绕过原记录。记录内部仍按原规则严格核对完整身份与配置 |
| 设备槽 | 可靠序列号使用 `serial-<摘要>`，路径不暴露原序列号；没有可靠身份则统一 `unverified`。同型号从未知身份转可靠身份、或反向变化时，含糊的旧待处理记录阻止建立新槽。不同可靠设备可各留记录，但同型号选择串行处理 |
| 目录内容 | 每型号最多 64 个已知格式设备槽；达到上限可重开已有槽，拒绝创建第 65 个。未知条目、过多目录、异常权限或重定向均拒绝选择，不自动修复或删除异常内容。型号锁目录自身存在恢复残留时也停止 |
| 锁与所有权 | 型号层 `JournalStore` 持有系统锁；设备层日志通过 `open_with_directory_guard` 保留目录、型号锁和全部祖先句柄。选择器或根对象先销毁不提前释放保护，所有日志释放后才允许重新选择 |

核心 `JournalStore` 销毁时显式 `unlock`，随后关闭文件并释放目录守卫，解决 Unix 上并发子进程短暂继承或复制文件描述符后、仅关闭原描述符仍占锁的问题。回归使用独立只读句柄证明旧锁释放后可重新取得，旧复制句柄关闭不会释放新锁；Windows 同时保留原有文件写入共享限制，没有为了测试改宽共享权限。

`DeviceDirectory::recovery_status` 先取得带目录守卫的日志锁，再查询残留。打开日志仍可能按核心既有规则继续已经验证的完成归档清理；这与只检查活动文件存在状态的 `JournalStore::recovery_status` 分开，不应把目录便利入口描述成完全不写磁盘的查询。全部处理均不发送设备报文。

系统 API 依据见 [Known Folder API](https://learn.microsoft.com/en-us/windows/win32/api/shlobj_core/nf-shlobj_core-shgetknownfolderpath)、[文件创建安全权限](https://learn.microsoft.com/en-us/windows/win32/fileio/file-security-and-access-rights)、[句柄安全信息](https://learn.microsoft.com/en-us/windows/win32/api/aclapi/nf-aclapi-getsecurityinfo)及 [CreateFileW 共享与重解析规则](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew)。显式解锁语义参考 [Rust File](https://doc.rust-lang.org/std/fs/struct.File.html#method.unlock) 和 [Windows 文件锁](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-lockfileex)。

保护范围是本地普通账户间的目录隔离和应用自身并发使用；不承诺防御同一用户主动修改权限、管理员接管或其他进程直接操作键盘。网络或重解析重定向的用户目录当前拒绝自动使用，保留原记录等待明确处理。稳定序列号资格仍由可信原生身份层保证，不能把未经核对的 HID 字符串填入 `serial` 即启用恢复；现有适配器继续传 `None`。

## 独立原生设备工厂与显式入口（应用已组合）

`native/core/src/controller.rs` 新增可信 `DeviceFactory` 和 `run_with_factory`。工厂负责设备预检及日志位置，控制器继续拥有输入/心跳、唯一设备线程、独立恢复预算和回复排空。原有固定目录 `run` 保留给开发模拟器与既有测试；外部消息仍只能选择型号和物理档位。

`native/windows/src/runtime.rs` 的接管顺序如下：

1. 有效握手及显式 `arm` 之前，不枚举或打开 HID，不创建恢复目录。握手、心跳及未接管退出只处理管道。
2. 工厂打开唯一 USB 控制集合并核对描述符，所选型号必须匹配。Windows 原生身份层要求直接 HID 字符串、缓存值、USB 父节点编号和唯一标记一致，且符合已核对家族的编号格式；缺失、占位或异常来源保持 `None`。没有命令行、网页或环境变量的序列号覆盖。
3. 身份资格满足后，`Lighting::open` 只读 A1/A0/D1，检查完整固件、布局、灯位及档位；此时无 D5/D2/F3/D6/D8/F5 或新基线。2.0.0.7 在此选择其独立规则；未知的 2.0.0.8 在目录创建和写入前拒绝。
4. 从固定 Known Folder 私有根选择对应设备槽，取得带目录守卫的日志锁。两个 RGB 档位或全局休眠存在任何待处理文件，均返回 `RECOVERY_REQUIRED`，不重新采样或建立播放基线；已验证完成记录可按既有规则续清理文件。工厂临时根与选择器释放后，保护由日志自身继续持有。
5. 控制器独立核对日志完整型号配置，再由 `Session::start_selected` 在同一持有句柄重新确认设备，执行既有备份、接管、绘图和恢复。恢复后释放本次日志，再接管时重新选择设备与日志，不复用旧句柄代次或路径。

设备预检返回后重新检查控制器停止信号；若此时已收到 EOF、退出或心跳失联，不再取得日志。操作系统打开设备和刷盘仍不承诺可被立即中断，原有故障验收要求保留。旧记录不会因接管而被自动恢复或删除；独立的原生 v2 查询/恢复操作须先检查，再由用户在恢复页面明确请求。

调试构建后可由可信开发后台选择新入口：

```powershell
target\debug\nuphylab-hid.exe --models desktop\windows\resources\models.json --lighting
```

这是需要 JSONL 握手和独立心跳的原生进程，不是普通用户播放命令。只接受一次 `--models` 与 `--lighting`，拒绝目录、身份、超时覆盖、重复参数和枚举混合模式。默认不加开关时仍为只读；应用驱动用同一可信程序路径单独构造灯光子进程，不向页面开放任意启动。现有运行 resources/binaries 未覆盖。

新入口握手的 `readOnly: false` 是协议能力，不证明某把键盘可以接管。AIR 的身份及 2.0.0.7 独立灯光规则已接通，但仍需可验证原状态；Mac 上只验证设备无关协议，实际打开设备返回 `WINDOWS_REQUIRED`。

## 唯一身份、应用接入与退出回执

### 原生唯一身份

`native/windows/src/identity.rs` 把身份来源与固件支持分开。当前规则仅开放已核对的 Air75 V3、VID/PID 19F5/1028 家族，逐次打开设备都重新读取证据，不保存一份前端可修改的“已授权编号”。

| 检查 | 规则 |
| --- | --- |
| 直接来源 | 对原生枚举得到的 HID 路径以元数据权限打开，直接调用 `HidD_GetSerialNumberString`；不把 hidapi 的缓存/回退结果单独当成证据 |
| 父节点 | Configuration Manager 从该接口定位设备树，最多向上检查五层，要求精确匹配该 VID/PID 的 USB 复合父节点及 `CM_DEVCAP_UNIQUEID` |
| 一致性 | 两次直接读取相同，且与枚举缓存及 USB 父实例编号逐字匹配；字符串和属性类型/长度均有界，错误时不给出序列号 |
| 格式与家族 | 当前已观察格式为 12 位 ASCII 十六进制；拒绝全零、全相同字符和已知占位串，未核对家族继续为 `None` |
| 公开状态 | 仅返回 `unverified`、`candidate`、`qualified`、来源及原因。原序列号、设备路径和父节点标识不进入页面或普通状态 JSON |

2026 年 11 月 9 日直接读取本机键盘的编号，与 USB 父节点一致；使用者换 USB 口重插后摘要相同，Windows 父节点唯一标记存在。新的 Rust 桥接和真实应用后台均报告 `qualified`。这验证的是本机这把设备的来源和重连稳定性；第二把同型号及其他型号仍待实体核对，不宣称所有设备已验收。厂商仍须遵守 USB 序列号的唯一性约定，ContainerID 或接口路径不是替代依据。

API 依据：[HID 内嵌序列号](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/hidsdi/nf-hidsdi-hidd_getserialnumberstring)、[Windows USB 序列号要求](https://learn.microsoft.com/en-us/windows-hardware/drivers/usbcon/usb-faq--introductory-level)、[实例编号和 UniqueID](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/instance-ids)、[容器冲突](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/avoiding-device-container-conflicts)。

### 应用中的基本播放

`server/windows-hardware.mjs` 为 Windows/Tauri 组合专用驱动，Mac 仍使用原 `Hardware`。只读子进程负责发现和身份；只有当前原生资格、型号、固件和档位均符合条件，应用才构造另一个 `NativeLightingClient`。启动路径由可信宿主提供，参数仅增加固定 `--lighting`，不把旧 `--backup` 参数或网页输入交给灯光进程。

- `windows-preview.json` 当前为版本 11：基本预览、播放与暂停使用字段白名单；两个异常恢复动作只接受操作名。Tauri 代理限制操作和参数，Node 再依据当前原生证据决定可用性；网页不能提供序列号、目录或资格值。停止不代替旧记录恢复；内置灯效、输入、声音与 AI 状态按各自条件开放，实体 AI 操作仍未完成。
- 持有灯光句柄期间，不用探针并行查询 USB；周期状态检查通过同一原生租约验证上一帧，核心对相同颜色检查身份、设置及日志，不重复颜色写入。成功恢复后可再次接管；换档时重新构造匹配的客户端。返回原侧灯时采用完整验证恢复后再接管，并重绘上一份主灯原始输出，不从当前颜色采样猜测侧灯备份，也不重复应用亮度。
- 旧桥接缺少身份字段时清除旧资格，不沿用前一连接。关闭或探针选择尚未结束时，迟到的接管不能再创建进程。动作失败保留原错误，不自动重启、重放或清空恢复记录。
- 精确 2.0.0.7、合格唯一身份及物理档位满足时，新后台开放逐键灯光和迎宾，原生事务仍逐次核对；休眠写入独立关闭。只读探针和显式灯效/休眠/功能键读取均保持无修改，旧窗口未替换。

### 正常退出与后台失联

`windows-host-v2.json` 单独管理宿主协议。宿主与 Node 均要求版本 2；旧资源必须重新准备配套版本，不能把旧 Node 的零退出码当作新协议的恢复证据。现有用户预览没有热替换资源。

1. Node 收到关闭或失联后，立即停止新调度并优先调用独立灯光客户端退出，再等待在途普通命令；退出不会排在颜色队列之后。
2. 灯光和只读探针各自清理。探针不拥有设置，不代签灯光恢复；只有只读协议允许跳过其无意义的灯光恢复步骤，Mac 默认关闭行为不变。任一后台清理失败仍尝试其余阶段。
3. 原生恢复完成及管道关闭后，Node 生成 `hostShutdownComplete`，回传宿主本次随机 64 字符十六进制退出编号、键盘验证、残留及无修改状态，并刷出回执后结束。动作失败但绑定的独立回滚已验证时，动作仍失败，正常关闭可成功；恢复未确认时回执失败。
4. 宿主必须同时核对本次回执、成功退出码和 stdout 完整结束；拒绝缺少、过期、重复、损坏、恢复失败或尾部异常的消息。失败状态保留，再次点击关闭不能绕过。正常等待最多 135 秒，失联检测为 15 秒，与原生独立心跳/恢复预算分开。

退出超时不强杀持有原记录的灯光进程。原生进程被强杀后只能保留日志，冷启动恢复已通过独立原生 v2 操作和页面确认接入；不会因打开页面或连接键盘自动调用 `recover_existing`。当前真实键盘验证了未接管时的只读退出，RGB 与休眠恢复及故障场景由模拟板/隔离进程验证，不能代替该固件实体恢复。

- **独立报文样本**：在无 HID、无网络的隔离 VM 中调用官方 S4 编码器，生成 15 份合成输入报文（D6/D8、F3、F5，覆盖三种密钥）。仅提交输入、64 字节报文、来源链接及摘要，不复制厂商代码、编号或设备数据。核心分别对照现有设置/逐键编码、单字节休眠设置及新只读 F3 编码。此结果只证明报文编码，不证明 2.0.0.7 的颜色量化、字段副作用、原调色板重建或恢复规则；实际写入须另按本轮固件证据和独立规则核对，编码样本本身不能授予资格。

`lighting-read-schemas.json` 只额外登记这个型号/精确版本的读取长度，Rust/Node 分别校验。型号默认仍为 1.0.23.6；此读取登记不提供主色反算、RGB 写入、休眠或恢复资格，2.0.0.7 的灯光规则在本轮单独登记，休眠写入仍关闭。读取结果仍固定 `restorationReady: false`。未登记 2.0.0.8 的负例继续在 D5/D2 前失败，新读取资格不影响原有恢复规则测试。

### 查询与明确恢复

该阶段契约为 `shared/contracts/native-lighting-v2.json`，版本 2、`coldRecovery: true`；本轮已升级为开头说明的 v3，默认只读协议不变。新旧独立灯光进程/客户端混用应拒绝握手，资源必须配套更新。页面的两个恢复动作由 Tauri 和 Node 各检查一次，只可提供操作名，不能附带型号、档位、目录、序列号、摘要或“已确认恢复”值。

| 页面动作 | 内部操作 | 行为 |
| --- | --- | --- |
| 检查待恢复记录 | `recoveryStatus` | 原生重新读身份与档位，选择固定私有位置，只打开已存在目录与锁；返回两个档位及整键盘休眠的残留，不创建或清理记录 |
| 确认恢复原设置 | `recoverExisting` | 要求同一原生进程已有检查，重新核对原生序列号、完整型号/固件/档位及活动原文；只处理当前档位与全局休眠，不获取播放租约 |

查询持有现有系统锁，使用 `JournalStore::open_existing`，并对 13 个可能的活动文件记录有界内容摘要；摘要和原始身份只留在原生内存。恢复前重新打开同一可靠设备和目录并逐项核对内容，缺少本次检查、设备变更、原文改动或丢失时，设备设置写入之前就拒绝。旧记录被删除不能成为恢复成功依据；应用对曾观察到的待处理项目及未确认的旧所有者另保留状态，空查询与普通 `restore` 不能清掉它。

当前 RGB 与全局休眠的恢复/完成标记清理分别执行。一项损坏、失败或异常展开后仍尝试另一项；只接受原有独立读回及已验证历史记录，失败原文保留。完成标记还需匹配当前可靠身份、完整固件和档位；已完成记录的清理与本次实际设备恢复分别报告，不重新播放。另一物理档位始终延后，不因文件消失或部分成功报告全部完成。

### 页面及退出行为

设备页新增“异常退出后的恢复”。页面本身不自动查询或恢复；检查后列出待处理的灯光档位与休眠，满足当前恢复固件时才启用“恢复原设置”。用户确认后，页面显示灯光、休眠、完成记录清理及延后档位的独立结果。切换连接、型号或物理档位会关闭旧确认框并清除旧显示；后端和原生仍独立重验身份。部分失败时要求重新检查后再明确操作，不自动重复写入。

实际 2.0.0.7 可以检查旧记录，新后台按独立灯光规则报告 `canRestore: true`；恢复时仍逐份检查固件及设备归属，不保证任意旧记录可以恢复。没有记录时显示未发现，不写成“已恢复”。无可靠身份或正在播放时禁用检查。私有历史原记录保留；没有记录的退出不能充当实体恢复证明。

恢复期间的心跳和优先退出继续由独立原生执行路径处理；一旦开始明确恢复，宿主失联不取消正在进行的清理，仍受独立预算约束。正常退出仍需本次宿主恢复回执、原生完整结束及无待处理状态；恢复失败、损坏完成记录或证据缺失不能变成成功退出，也不强杀原生所有者。
